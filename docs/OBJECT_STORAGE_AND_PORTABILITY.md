# Object storage and infrastructure portability

## Contract

Application and domain code depend on `ObjectStoragePort`, not a cloud SDK. The
production adapter implements the port with standard S3 operations and AWS
Signature Version 4. Endpoint, region, bucket, credentials and path-style mode
are installation configuration. Hetzner Object Storage, Cloudflare R2, AWS S3
and MinIO can therefore be evaluated or replaced without changing media domain
logic.

The bucket is private. The API creates short-lived, operation-specific signed
URLs. Browser uploads go directly to object storage and do not proxy media bytes
through Web or API. Object keys are generated by the server and constrained to
`tenant/<tenant-id>/media/<asset-id>/<variant>`; callers cannot select another
tenant prefix.

Finalization checks the expected byte count, a server-computed SHA-256 checksum,
signed declared MIME type and MIME detected from stored bytes before scanning
and accepting an asset. The API streams the stored object through SHA-256 with
constant memory; when a provider also returns a checksum, both values must
match. Client-controlled S3 metadata is not accepted as checksum evidence.

## Configuration

Non-secret settings:

- `OBJECT_STORAGE_MODE=s3_compatible`
- `OBJECT_STORAGE_ENDPOINT=https://<s3-endpoint>`
- `OBJECT_STORAGE_REGION=<provider-region>`
- `OBJECT_STORAGE_BUCKET=<private-bucket>`
- `OBJECT_STORAGE_FORCE_PATH_STYLE=<provider requirement>` (`true` is validated
  for this installation's Hetzner regional endpoint and is commonly used by
  MinIO)

Secret-file settings:

- `OBJECT_STORAGE_ACCESS_KEY_ID_FILE`
- `OBJECT_STORAGE_SECRET_ACCESS_KEY_FILE`

Direct values remain available for non-Compose runtimes, but production
operators should inject secret files or resolve equivalent secret references.
Credentials must be bucket-scoped where the provider supports it and must never
be exposed to the browser. Only signed URLs leave the API.

## Bucket policy and CORS

- Keep public access disabled.
- Permit the runtime credential only the required bucket/object operations.
- Allow browser `PUT` only from the exact configured Web origins.
- Allow request headers `content-type` and `x-amz-checksum-sha256`.
- Expose only headers required by the uploader; do not use wildcard origins with
  credentials.
- Enable versioning/lifecycle policy and abort incomplete multipart uploads.
- Keep retention and backup policy aligned with database media metadata.

## Readiness and replacement

Readiness performs a bucket-scoped `HeadBucket` through the same configured
adapter. Changing provider requires new configuration, a controlled object copy,
key/count/checksum reconciliation and then an endpoint switch. Database object
keys do not contain provider URLs, so they remain valid after migration.

Before staging promotion, `npm run storage:probe` must pass against the real
bucket. It performs a signed write, streaming integrity read, signed download
and cleanup without using application database state.

PostgreSQL, object storage and secret storage are independent persistence
boundaries. App containers hold no permanent media. Replacing an API, Web or
worker container does not remove persistent data.

## Current limitation

The first production adapter deliberately uses signed single-object `PUT`. It
does not claim resumability when the backend asks for multipart. This is safe for
the current bounded upload limits but large-upload resume is not yet a production
capability. A later multipart capability must add create/sign-parts/complete/
abort semantics to the port and API, with persisted upload state and integration
tests. It must not emulate multipart in process memory.

## Single-node to multi-node

1. Start with Web, API, worker and PostgreSQL under Docker Compose, plus external
   S3-compatible storage.
2. Move PostgreSQL by changing database URLs after backup/restore and validation.
3. Run additional workers; PostgreSQL job claiming and idempotency protect
   at-least-once execution.
4. Run additional Web/API instances behind a trusted load balancer. Sessions,
   OAuth transactions, audit and jobs remain in PostgreSQL.
5. Add a broker only after measured queue pressure; keep it behind the queue
   boundary and preserve transactional outbox semantics.

No step requires rewriting media or business domain logic.
